# 256k 多轮记忆压力测试：ActKV 开 vs 关

- 日期: 2026-10-10
- 目的: 在**多轮连续对话**、**真实内容（代码库）**、**约 256k 上下文**下，比较 ActKV 开/关的记忆召回能力
- 每轮都是**全新进程**（先关闭旧进程、确认端口释放、再重启），保证历史 KV 被清空

## 0. 两个配置的差异（仅此两行）

| | ON | OFF |
|---|---|---|
| `--kvmem-action-lrfu --kvmem-lrfu-lambda 0.50 --kvmem-lrfu-top-frac 0.90` | 有 | 无 |
| `--kvmem-score-agg max` | 有 | 无 |

其余完全相同：Qwen3.8-27B-IQ3_S、`-c 262144 -n 16384 -b 512 -ngl 99`、`--kvmem-budget 36864`、
`--kvmem-gen-reserve 16384`、`-ctk/-ctv q8_0`、MTP draft n_max=3、thinking medium + rbudget 8192。
提问走贪心解码（`temperature=0`）。

## 1. 测试方法（比"埋一句话"更接近日常使用）

- **干草堆**：确定性生成的**多模块代码库 dump**，883,707 字符 = **232,781 prompt tokens**
  （真实感的 Python 模块：dataclass 配置、async 处理循环、日志、类型注解、注释）。
- **16 个"代码里的针"**：真实工程里会被问到的细节 —— 错误码 `ERR-4471`、读超时 `8412`、
  队列名 `ingest-v3-eu-west`、特性开关 `FEATURE_SHARD_REBALANCE_V2`、盐前缀 `sk_live_9f42c`、
  TODO 归属人 `alina.kovacs`、cron `*/7 3 * * 1-5`、表名 `tenant_shard_map_v7`、
  信号 `SIG_REBALANCE_DONE`、指标 `ingest.rebalance.lag_seconds`、S3 桶、草稿模型 id、
  类名 `ShardRebalanceCoordinatorV3`、缓存 TTL `5417`、topic `ingest.events.v9`、
  退避 profile `exp-jitter-8`。问题用自然语言提问，不点名文件位置。
- **8 个"对话中的针"**（真正考多轮记忆）：某一轮用户顺口提到一个事实
  （如"staging tenant id 是 t-9f42c"），**6 轮之后再问**该事实。
- **8 个普通轮次**（重构/总结/权衡）用于制造上下文扰动。
- 共 **40 轮**；每轮追加问题与回答，最终**活跃上下文 ≈ 234k–235k tokens**（窗口 `-c 262144`）。
- 计分：回答中出现期望的唯一字面量即为命中（大小写/标点归一化）。

## 2. 结果：两者可复现地不同

| 配置 | 轮次 | 代码里的针 | 对话中的针 | 合计 | 未命中 |
|---|---|---|---|---|---|
| **ON**（第 1 次） | 40 | **16/16** | **8/8** | **24/24 = 100%** | — |
| **ON**（第 2 次，重启进程） | 40 | **16/16** | **8/8** | **24/24 = 100%** | — |
| **OFF**（第 1 次） | 40 | 15/16 | 6/8 | **21/24 = 87.5%** | t32, t33, t35 |
| **OFF**（第 2 次，重启进程） | 40 | 15/16 | 6/8 | **21/24 = 87.5%** | **t32, t33, t35（完全相同）** |

- 两次重启复跑，**ON 都是 24/24，OFF 都是 21/24，失败的题号完全一致**（贪心解码，确定性）。
- OFF 的三次失败：
  - t32（对话记忆，期望 `2026-11-20`）答 "The deadline agreed" 后停止
  - t33（对话记忆，期望 `t-9f42c`）答 "The staging tenant ID you" 后停止
  - t35（代码针，期望 `ingest.events.v9`）答 "The ingest" 后停止

### 回答风格也系统性地不同

| | 生成 token 中位数 | 生成 <15 token 的题数 | 单轮时延（均值） |
|---|---|---|---|
| **ON** | **6** | 24/24 | **2.51–2.80 s** |
| **OFF** | **43** | 5/24 | **2.98 s** |

ON 下模型几乎总是**直接给值**（"`8412`"、"`ERR-4471`"，2–13 token）；
OFF 下倾向先复述问题再作答（中位数 43 token），并且在 3 个问题上**提前 EOG**（`finish_reason=stop`，
只生成 2–5 token），因此既没答出值、也拖慢了整轮。

## 3. 这 3 次失败是什么性质（重要限定）

- 两个 arm 的服务端日志里**没有任何错误**（无 `no free GPU slot`、无 decode failed、
  无 CUDA 异常），所以**不是 KVMem 的解码事故**；
- `finish_reason=stop` = 模型自己结束回合，即"没答出来"，**不是答错值**；
- 它们是**由不同的 KV 选择导致的**：两边 prompt 逐字节相同、贪心解码、同版本服务端，
  唯一变量就是选中的工作集（ON 用 LRFU 时序保留 + GQA-max，OFF 用一次性余弦 + 折叠均值）。
- **但要注意噪声下限**：在更小的 18k dump 冒烟测试里，ON 配置也出现过 4 次同类提前终止
  （见 `dialog-smoke.json`）。所以"提前终止"本身是模型侧现象、与内容相关；
  本次 256k 工作负载下它**只在 OFF 复现两次**，这是配置差异而非单次抖动。
- 结论口径：**ON 在本负载下 24/24 全部答对且可复现；OFF 复现性丢 3 题。**
  若要把"检索失败"与"生成长度/提前终止"彻底分离，可以给未命中题加一次重问
  （同会话内重问，值仍在窗口里则应答出）——我可以补跑这个对照。

## 4. 速度（同一负载）

### Prefill（232,781 tokens 一次性投喂）

| 配置 | 运行 | 墙钟 | 速率 |
|---|---|---|---|
| ON | r1 | 524.2 s | 445 tok/s |
| ON | r2 | 406.9 s | 574 tok/s |
| OFF | r1 | 504.9 s | 462 tok/s |
| OFF | r2 | 406.2 s | 575 tok/s |

→ **406–524 s（6.8–8.7 分钟）**，445–575 tok/s；两个配置无差别，波动来自运行间抖动。

### Decode（各轮生成聚合，仅统计 token-eval 时间）

| 配置 | 聚合吞吐 | 说明 |
|---|---|---|
| ON | **35.8 tok/s** | 每题中位 6 token，固定开销占比高 |
| OFF | **41.3 tok/s** | 每题中位 43 token，摊薄了固定开销 |

- 单轮端到端时延：ON **2.51–2.80 s**，OFF **2.98 s**（ON 更快，主要因为输出更短）。
- 与之前的 256-token 长生成探针（250k 窗口下 27.9–34.0 tok/s）同一量级。

## 5. 一句话结论

在 232.8k tokens 代码库 + 40 轮连续对话（最终 ~235k 活跃上下文）的真实化负载下：
**开 ActKV 两次复跑均 24/24（100%）；关掉后两次均 21/24（87.5%），且失败题号与失败方式完全一致。**
开 ActKV 时模型回答更短更直接（中位 6 vs 43 token），单轮也更快。
prefill 两者相同（407–524 s）。
