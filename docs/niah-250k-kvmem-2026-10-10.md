# KVMem 250k 上下文召回测试(gkamradt Needle-in-a-Haystack 方法)

- 日期: 2026-10-10
- 被测: `I:\llama\kvmem-llama.cpp-0.17.0\build-cuda13.4-dll\bin\start-llama-server.bat`
  (Qwen3.8-27B-GSQ-RCO-IQ3_S-mtp, `-c 262144`, `--kvmem-budget 36864`,
  `--kvmem-gen-reserve 16384`, `--kvmem-action-lrfu` λ=0.50 p=0.90,
  `--kvmem-score-agg max`, `-ctk/-ctv q8_0`, MTP draft)
- 硬件: 单卡 RTX 5060 Ti 16 GB(本地实际只有一张卡;脚本注释里的 5050/5090 不适用)
- 方法来源: Greg Kamradt 的 needle-in-a-haystack(技能未安装,按其方法复刻)

## 1. 结论

| 项目 | 结果 |
|---|---|
| 上下文(实测 prompt tokens) | **252,728** |
| 针数 / 命中 | **12 / 12** |
| **召回率** | **100.0%** |
| 规划器实际参与注意力(attention window) | **36,791 tokens = 上下文的 14.6%** |
| 首次 prefill | 618.8 s(409 tok/s) |
| 每次提问(question→answer) | 2.6 – 3.1 s |
| 逐深度 | 0%, 9.1%, 18.2%, …, 100% **全部命中**(中段 45%/54%/63%/72% 也命中) |

即:**在 250k 上下文下,服务端只把约 14.6% 的上下文放进注意力窗口,12 个埋在不同深度的针全部被检索回来并正确回答。**

### 关键证据(不是推断,是服务端自报)

开启 `KVMEM_TRACE=1` 后,每轮选择都会打印窗口大小:

```
KVMEM_TRACE retrieval stage_in=220 stage_out=253 skip=10 gpu_reused=68 window=36791 free_slots=61
KVMEM_TRACE retrieval stage_in=90  stage_out=90  skip=26 gpu_reused=198 window=36823 ...
KVMEM_TRACE retrieval stage_in=29  stage_out=29  skip=41 gpu_reused=259 window=36861 ...
...
KVMEM_TRACE prefill_pressure stage_in=288 stage_out=108 skip=1 gpu_reused=0 window=36864   (prefill 期间共 15 次)
```

- `window=36,79x` 是**选中块的总 token 数**,即真正参与 attention 的上下文;
- `stage_in + gpu_reused = 288` 块 × 128 tokens/块 = 36,864 ≈ budget,与 `--kvmem-budget 36864` 完全吻合;
- 选择分数横跨整段上下文(block id 从 0 一直到 1900+),说明检索是**全历史内容检索**,不是"只看尾部"。

## 2. 方法(gkamradt 式)

`gkamradt/needle-in-a-haystack` 的原始流程是:构造长干草堆 → 在若干深度埋入唯一事实 → 提问 →
按"答案是否命中"记分 → 画深度×上下文长度的热力图。本次做法:

1. **干草堆**(确定性生成,可复现):编号日志段落 + 词表轮换,929,880 字符 ≈ 252.5k tokens;
2. **12 根针**:唯一访问码(`BLUEBIRD-100`, `ORCHID-107`, …),按字符深度 0%、9.09%、…、100%
   等距插入;每根针的句子与其问题共享关键词(如 "orchid checkpoint"),与 gkamradt 原版
   "问题与针句高重叠"的设置一致;
3. **一次 250k prefill**(turn 1,埋在最后的指令让它回 `ACK`),随后 **12 个问题在同一个会话里
   逐轮提出** —— 每轮问题成为新的检索 query,KVMem 每轮重新选择工作集;
4. **计分**:答案中是否出现该针的精确访问码(大小写/标点归一化)。

> 为什么不是"每个深度各跑一次 250k":那需要 11 次 250k prefill(约 2 小时),而逐轮提问在
> 一次 prefill 后给出同样的逐深度分辨率,并且顺带压测了多轮检索路径。

## 3. 判别性对照(证明这个测试不是"白给分")

100% 召回本身不能说明问题——必须证明**被驱逐的 KV 真的看不见**。做了一组同构对照:

配置:`-c 65536`, `--kvmem-budget 4096`, `--kvmem-gen-reserve 4096`, 35,479-token 干草堆,
4 根针(0% / 33% / 67% / 100%),窗口实测 ≈4,000 tokens(上下文的 11.3%)。

| 模式 | 窗口 | 召回 | 未命中回答 |
|---|---|---|---|
| **retrieval**(启动器配置) | 3,969–4,060 | **4 / 4** | — |
| **recency**(无检索,仅 sink+最新) | 4,096 | **2 / 4** | "The log does not provide an access code for the orchid checkpoint." |

结论:
1. **驱逐是真实生效的**:recency 模式下 33%/67% 深度的针被换出后,模型明确表示日志里没有该访问码
   —— 说明被 `seq_rm` 的 cell 确实不参与 attention;
2. **测试是可失败的**:同一干草堆、同一模型,retrieval 4/4 vs recency 2/4;
3. 因此 250k 下的 12/12 可以归因于检索,而不是"模型本来就能看到全文"。

## 4. 一处未解释的异常(如实记录)

250k 上做同样对照时,`--kvmem-method recency` **也拿到 12/12**:

```
method=recency, -c 262144, prompt_tokens=252728  ->  12/12 = 100.0%
```

按代码路径,recency 模式下 prefill 压力路径
(`prepare_working_set` → `maybe_offload_during_prefill`, `llama-memory-kvmem.cpp:2304-2313`)
并不按 method 分支,应当同样把窗口压到 36,864 tokens,那么 9%–81% 深度的针应当 MISS。
实际全部命中,**与 32k 对照的行为矛盾**。

- 这**不影响**第 1 节的结论(retrieval 那次的窗口与命中是服务端 trace 直接记录的);
- 但它意味着 **250k 的 recency 这次不能作为负对照**,其行为原因未查明(可能与该次运行的
  prefill 压力触发情况/会话状态有关);
- 建议后续用一个明确可复现的方式再确认(例如 250k + recency + `KVMEM_TRACE=1`,
  直接读 `prefill_pressure window=` 行),这属于"方法学"问题,不是本次召回结论的组成部分。

  --mmproj "I:\model\mmproj-Qwen3.8-27B-Q5_K-MIX.gguf" --no-mmproj-offload --image-max-tokens 256 `

  --kvmem-budget 36864 --kvmem-gen-reserve 16384 `
  --kvmem-action-lrfu --kvmem-lrfu-lambda 0.50 --kvmem-lrfu-top-frac 0.90 --kvmem-score-agg max `

## 6. 与启动器 `.bat` 的差异(必须声明)

| 项 | `.bat` | 本次实测 |
|---|---|---|
| 启动方式 | `start-llama-server.bat`(末尾 `pause`) | 直接用 exe + 同一套参数(便于后台管理与读日志) |
| `--host` | `0.0.0.0` | `127.0.0.1` |
| 提问时的 `reasoning_effort` | 模板默认 `medium` | 每题显式 `none`(关闭思考,避免 12×(最多 8192) 思考 token 拖垮测试;服务端本身仍以 `medium` 启动) |
| `KVMEM_TRACE` | 未开启 | 开启(仅用于取得窗口证据;开启会拖慢,故 prefill 耗时应以未开启那次为准) |

对召回结论无影响的差异:`--host`;可能有影响的差异:提问时的 thinking 关闭(若开启 thinking,
模型在"上下文确实没有该信息"时更可能长时间搜索,但对这 12 个命中题目的影响待验证)。

## 7. 局限

1. **中段只测了 12 个深度点**,不是热力图;250k 下未做多上下文长度扫描;
2. **针与问题共享关键词**(与 gkamradt 原版一致),因此测的是"检索能否找回",不是"语义改写下的鲁棒性";
3. **无 FullKV 上界对照**:262k 全量 KV 在 16 GB 卡上放不下,无法在同一硬件上跑 FullKV 基线;
4. **单次运行**:每个配置只跑了一次,未做多 seed 重复(温度参数不影响本测试的确定性,但未做重复实验);
5. 250k recency 异常未解释(见 §4)。
